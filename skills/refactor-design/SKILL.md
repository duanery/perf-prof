# 模块抽取 / 分层重构流程

**目标**：人只在一个决策点上花精力——确认分层表和头文件；边界的推敲由 AI 按准则完成，
不靠人一版版 review 实现来逼出来。

**准则唯一来源**：`AGENTS.md`（即 `CLAUDE.md`）的「模块边界设计准则」。本技能不复制准则，
每次使用时现读，复盘时也追加到那里。

**范例**：`src/filter/event_filter.c` + `filter.h`（event_filter / pid_filter，被 task-state、rundelay 共用），
AGENTS.md 准则里的正例、反例都取自它。

## 阶段 0：问题与使用者（人给出，AI 补全）

开始前确认以下内容，缺的向用户问，不要自己假设：

- **问题**：现状哪里重复、哪里出错、哪里扩展不动（写成 plan 的"问题"一节）。
- **现有使用者**：哪些 profiler / 模块会调用新接口。
- **未来使用者**：至少一个，可以是设想（如通用的 `follow=pid` 事件属性、按其它字段的过滤）。
  它是检验"留没留余地"的唯一标尺。
- **约束**：兼容的内核版本、性能热路径、不可改动的部分。

AI 先读现有使用者的代码，列出它们之间重复的逻辑与各自特有的逻辑，作为阶段 1 的输入；
并查 `docs/modules.md`，已有模块能承担的部分复用或扩展它，不另起一个。

## 阶段 1：接口稿（AI，不写实现）

在 `docs/plans/YYYY-MM-DD-<topic>-design.md` 写，**这一阶段不改任何 `.c`**。必须包含：

1. **分层表**——最关键的产物：

   | 层 | 位置 | 职责 | 不管 |
   |---|---|---|---|

   "不管"一列必须填：它列出本层**不认识**的类型和**不做**的决定。

2. **原则**：本次重构对准则的具体落实（如"过滤器只产出字符串"）。
3. **头文件草稿**：完整的 `.h`，不透明类型、生命周期顺序、每个函数的返回值语义、
   `ops` 回调的调用时机与返回值的效果。
4. **生命周期图**：new → 初始值 → start → 运行期 → free；写明初始值从哪来、第一次的结果怎么拿到。
5. **状态表**：模块内每一份状态的含义、何时变化、谁查询，一张表：状态 / 内部表示 / 含义 / 何时变化 / 谁查询。
6. **调用方伪代码**：每个现有使用者一份，**加上未来使用者一份**。未来使用者若需要改接口，
   回到第 3 步改接口，而不是写一个"以后再说"。
7. **扩展点与非目标**：哪些将来可以做、从哪一层接入；哪些明确不做。
8. **依赖的内核约束**：方案建立在哪些内核行为上（长度上限、写入顺序、通知语义、分配规律……），
   每条写出内核出处、引入版本，标明是否已在 v3.10 与最新内核源码上核实；已登记在
   `docs/kernel_dependencies.md` 的直接引用其编号。约束不成立时方案是退化还是出错，也要写明。

## 阶段 2：独立审查（另一个 AI）

用 Agent 工具起一个**新的**子代理（不要用 fork，审查员不应继承实现者的思路），
只给它：plan 文件路径、`AGENTS.md` 的准则节、现有使用者的源码路径。要求它：

- 逐条准则给出 通过 / 违反 / 不适用，违反的指出 plan 中的具体位置和改法；
- 用调用方伪代码反推：调用者是否读了内部字段、是否出现两份相似代码、
  是否要遵守多步协议、是否替模块决定时机；
- 未来使用者能否不改接口接上；
- 给出 2–3 个边界画法的对比（各自的"不管"列有何不同）和推荐；
- 方案依赖的内核约束是否都列出且核实，有没有把内核行为当成理所当然却没写出来的；
- 不要求它称赞，只要问题。

实现者据此修改 plan，**有分歧的点不要自行裁决**，连同两方理由列入 plan 的"待确认"一节。
重复审查直到没有"违反"项（最多 3 轮，仍有分歧交给人）。

## 阶段 3：人确认（唯一的人工决策点）

向用户呈现：分层表、头文件草稿、未来使用者的伪代码、待确认项。不要让用户读实现。
用户的结论逐条写入 plan 的"已确认"一节，编号列出，后续实现以此为准。

用户在这一步提出的修改，若能概括为通用判断，**当场**按阶段 5 追加准则。

## 阶段 4：实现

1. **先写模块的单元测试**：桩掉定时器、回调等外部依赖，覆盖生命周期各阶段与边界条件，
   在 valgrind 下跑，无泄漏。
2. 实现模块，再逐个迁移使用者，最后删除被取代的代码。
3. 按 AGENTS.md「提交拆分」：模块、每个使用者、删除无用代码、测试、文档各自单独提交；
   每步 `make`，迁移一个使用者后跑它的 pytest（先 `cd tests`）。
4. 新模块或接口变化登记到 `docs/modules.md`（源码 / 能力 / 注意事项 / 内核功能），实现中踩到的坑写进注意事项，随文档提交。
5. 依赖内核约束的代码按 AGENTS.md「内核依赖：代码注释 + 登记」写 `Kernel constraint:` 注释，
   并在 `docs/kernel_dependencies.md` 新增或更新条目的依赖位置（随文档提交）。
6. 实现与接口稿不一致之处，记入 plan 的"实现与本稿的差异"一节，并说明原因。
   **若差异改变了头文件或分层表，停下来回到阶段 2**，不要在实现里悄悄改边界。

## 阶段 5：复盘（每次必做）

人在阶段 3、4 以及之后 review 中提出的每一条修改意见，逐条判断：

- 是本次特有的事实（某个字段）→ 只记入 plan；
- 是内核行为 → 按 AGENTS.md「内核依赖」写代码注释并登记到 `docs/kernel_dependencies.md`；
- 是边界判断（谁持有、谁决定、谁认识谁）→ **提炼成一条准则，追加到 AGENTS.md
  「模块边界设计准则」**，附正例 / 反例。追加前检查是否能并入已有条目
  （例如"边沿通知回调"本质是"向上依赖用回调反转"的特例）。

返工的旧版本可留在本地分支，plan 中写明每一版的问题，它们是提炼准则的原始材料；
追加到 AGENTS.md 的准则只写正例 / 反例本身，不引用本地分支。

plan 落地后按 AGENTS.md「设计文档（plan）」回填 `Status:`。

## 检查清单（阶段 1 交付前自检）

- [ ] 分层表的"不管"列每层都填了
- [ ] 头文件里没有结构体定义、没有使用者的概念（角色、下标、具体字段名）
- [ ] 初始值如何加入、第一次结果如何得到，有明确答案
- [ ] 每个回调写明调用时机、返回值如何影响模块状态
- [ ] 调用方伪代码里没有两份相似代码、没有多步协议、没有替模块判断时机
- [ ] 未来使用者的伪代码不需要改接口
- [ ] 扩展点与非目标已列出
- [ ] 依赖的内核约束已列出，出处与版本已在内核源码上核实
